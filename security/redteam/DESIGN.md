# 레드팀 운영 설계 — 더 똑똑한 헌터, 정보를 공유하는 에이전트

run-1은 헌터 7명이 각자 맡은 하위 시스템만 보고 따로 보고했다. 서로 무엇을 찾았는지 몰랐고, 단독으로는 취약점이 아닌 발견은 "하드닝 메모"로 흩어졌다. 그 결과 **두 구성 요소 사이에서만 성립하는 문제**를 볼 방법이 없었다.

이 설계는 [`JANUS-SEC/ZeroMDASH`](https://github.com/JANUS-SEC/ZeroMDASH)(커밋 `9cb2752`, Microsoft MDASH의 공개 재구현)의 장치 네 가지를 가져와 그 공백을 메운다. ZeroMDASH를 통째로 실행하지는 않았다(§8).

| ZeroMDASH의 장치 | 여기서 만든 것 | 상태 |
|---|---|---|
| 도메인 불변식 레지스트리 | `registry/domain-invariant-registry.json` | run-1 사실로 작성, ZeroMDASH 스키마의 필수 필드 충족 |
| primitive와 capability 어휘 | `registry/capabilities.json` | run-1 후보 21건의 capability 뷰 |
| 결정론적 체인 사전 필터 | `chains.py` → `registry/chain-candidates.json` | 체인 가설 21개 산출 |
| 가설 원장·반례 시도·비평가 관점 | `briefs/hunter-brief-v2.md` | 프롬프트. 아직 에이전트에 써 보지 않음 |
| 공유 워크스페이스 | `board.py` | 테스트 통과. 실제 에이전트 실행에는 아직 안 씀 |

## 1. 헌터가 더 똑똑해지는 지점

### 1.1 파일이 아니라 seam을 맡긴다

run-1 배정 단위는 "ShinkaEvolve 웹 UI", "벤치마크 하네스" 같은 하위 시스템이었다. v2 배정 단위는 레지스트리의 **seam**, 곧 한 구성 요소가 보장한다고 믿는 것과 다음 구성 요소가 가정하는 것이 만나는 자리다.

예: `SEAM-stored-text-to-dom`(모델이 쓴 필드가 DB에서는 안전하다가 UI가 렌더링할 때 스크립트가 된다)과 `SEAM-ui-script-to-same-origin-api`(UI 페이지의 스크립트는 외부 페이지가 못 읽는 같은 출처 엔드포인트를 부를 수 있다). run-1에서는 앞의 것을 웹 UI 헌터가, 뒤의 것을 아무도 보지 않았다. 둘을 이으면 "결과 디렉터리를 건네준 사람 → 뷰어 XSS → 뷰어 머신의 파일 읽기"라는 가설이 나온다.

### 1.2 레지스트리를 먼저 읽고, ID로 말한다

헌터는 코드를 읽기 전에 레지스트리에서 자기 seam의 엔티티·표현·불변식·전이를 읽는다. 보드에 올리는 모든 글은 레지스트리 ID를 topic으로 단다. 그래야 서로 다른 헌터의 관찰이 같은 대상에 대한 것인지 기계적으로 묶인다.

레지스트리는 색인이지 증거가 아니다. 항목을 근거로 쓰려면 적힌 위치를 직접 다시 읽는다.

### 1.3 가설 원장과 반례 시도

헌터는 산문 대신 가설 목록을 관리한다.

- 맡은 seam의 불변식마다 가설을 하나 이상 세운다. 조사 중 새 경로·새 표현·새 생명주기 전이를 발견하면 가설을 **추가**한다. 지우거나 합치지 않는다. 합칠지는 비평가가 정한다.
- 가설을 닫기 전에 반례를 시도한다. "막혀 있다"고 결론 내리려면 그 sink에 닿는 **모든** 경로를 열거해야 한다. 기준 경로 하나가 안전하다는 것은 우회 경로가 안전하다는 증거가 아니다.
- 못 푼 조합은 `unresolved`로 남긴다.

### 1.4 네 갈래에서 가설을 뽑는다

ZeroMDASH의 계획자 넷에 대응한다.

| 갈래 | 이 리포에서의 재료 |
|---|---|
| 명세 | 코드와 문서가 **스스로 주장하는 것**. `scientific_cases.py`의 "정답은 절대 받지 않는다", `evaluation.py`의 "타임아웃이 시작한 모든 것을 죽인다", CodeEvolve README의 "sandboxed". 주장과 코드가 어긋나는 곳이 가설이다 |
| 유사 소프트웨어의 이력 | 같은 부류(생성 코드를 실행하는 진화 탐색 프레임워크, 연구용 로컬 웹 뷰어)에서 반복된 결함 유형: 재개 시 pickle, 공유 임시 디렉터리, 뷰어 경로 탈출 |
| 대상의 패치 이력 | 벤더링된 세 프레임워크의 업스트림 커밋(`baselines/setup_baselines.sh`에 적힌 SHA 이후)에서 보안 수정을 찾고, 같은 결함의 형제 경로가 남았는지 본다 |
| 새 기능 | 가장 최근에 붙었고 검토가 덜 된 곳: OpenEvolve manual 모드, CLI 에이전트 백엔드, 정적 내보내기, ShinkaEvolve 스킬 |

### 1.5 결과 분류에 primitive를 둔다

run-1의 분류는 `candidate / covered / blocked`뿐이라, 능력은 확인됐지만 단독 영향이 없는 발견이 후보로 과장되거나 메모로 묻혔다. v2의 결과 유형:

| 유형 | 뜻 | 다음 |
|---|---|---|
| `standalone` | 그 자체로 경계를 넘는 직접 영향이 있다 | 검증 → 승인 → PoC |
| `primitive` | 메커니즘·도달 가능성·공격자 통제·획득 능력은 소스로 확인되지만 단독으로는 영향이 닫히지 않는다 | 보드에 올림 → 체인 계획 |
| `observation` | 보안 관련 사실이지만 체인 재료로 쓰기엔 부족 | 하드닝 메모 |
| `rejected` | 소스가 반박한다 | 보드에 `dead_end`로 남겨 중복 조사를 막음 |
| `inconclusive` | 증거 부족 | 미해결 사실을 적어 다음 실행으로 |

primitive는 **단독으로 취약점으로 보고하지 않는다.** `capabilities.json`에서 `terminal_impact`가 `null`인 6건(`wildcard-bind-no-auth`, `cors-wildcard-json-api`, `dom-xss-llm-derived-fields`, `sidebar-innerhtml-unescaped-llm-text`, `time-limit-process-escape`, `context-bundle-fence-breakout`)이 여기에 해당한다.

### 1.6 비평가는 관점을 바꿔 가며 반박한다

비평가는 헌터가 인용한 위치를 직접 열어 확인하고, 관점을 **둘 이상** 골라 적용한다. ZeroMDASH의 `presets/skills/`에는 특정 연구자의 사고방식을 정리한 관점 팩이 있다. 대부분 메모리 안전·커널 쪽이라 이 Python/웹 대상에는 클라우드·AI 인프라 격리 쪽(`hillai-ben-sasson`, `shir-tamari`, `nir-ohfeld`, `felix-wilhelm`)과 로직·파서 쪽(`tavis-ormandy`)이 맞는다. 관점 팩은 사용 전에 실제 파일을 읽는다. 요약만 인용하지 않는다.

## 2. 정보 공유: 보드

`board.py`는 실행 디렉터리 안의 JSONL 추가 전용 로그다.

```
<run>/agents/<agent-id>/scratch/outbox.jsonl   각 에이전트가 자기 것만 쓴다
<run>/board.jsonl                              조정자가 sync로 병합한 정본
```

- **쓰기 격리.** 에이전트는 자기 outbox에만 쓴다. 공유 파일은 조정자만 쓴다. run-1에서 지킨 "공유 파일의 작성자는 조정자 하나"라는 규칙이 그대로 유지된다.
- **읽기는 열려 있다.** `read`는 모든 outbox를 훑는다. 동시에 도는 에이전트가 조정자를 거치지 않고 서로의 글을 본다.
- **`--new`** 는 이전에 받지 않은 글만 준다. 에이전트는 시작할 때, 가설을 닫기 전, 끝내기 전에 읽는다.

### 글의 종류

| 종류 | 누가 | 위치 인용 | 용도 |
|---|---|---|---|
| `fact` | 조정자·정찰·헌터·비평가·체인 | 필수 | 확인한 소스 사실 |
| `lead` | 〃 | 선택 | 조사할 가치가 있는 가설. 자기 seam 밖이면 주인에게 넘어간다 |
| `primitive` | 헌터·비평가 | 필수 | 필요 능력과 획득 능력을 어휘로 적은 능력 |
| `dead_end` | 〃 | 필수 | 반박된 생각과 이유 |
| `handoff` | 정찰·헌터·체인 | 필수 | seam을 건너가는 객체 |
| `question` / `answer` | 전원 | 선택 | seam 주인에게 묻고 답한다 |
| `claim` / `release` | 헌터·비평가·체인·PoC | 선택 | "이건 내가 본다". 같은 topic의 두 번째 claim은 거부된다 |
| `challenge` | 비평가 | 필수 | 헌터 주장에 대한 구체적 반박 |
| `verdict` | 비평가 | 필수 | 판정. 조정자만 본다 |
| `chain_candidate` | 체인 | 선택 | 체인 가설 |
| `directive` | **조정자만** | 선택 | 배정과 라운드 전환 |

### 공유가 만드는 위험과 대응

| 위험 | 대응 |
|---|---|
| **프롬프트 인젝션의 전파.** 헌터가 대상 리포에서 읽은 문장에 지시가 숨어 있으면 보드가 그것을 다른 에이전트에게 옮긴다 | 보드 글은 데이터다. `read` 출력 맨 위에 그 문장이 붙고, 브리프도 같은 말을 한다. `directive`는 조정자 역할만 올릴 수 있고, 남의 outbox에 끼워 넣은 글은 소유자 불일치로 거부된다. 본문은 2,000자로 제한한다 |
| **근거 없는 주장의 확산** | `fact`·`primitive`·`dead_end`는 `path:line` 없이는 올라가지 않는다. `--target`을 주면 파일 존재와 줄 범위까지 검사한다. 읽는 쪽은 위치를 다시 읽은 뒤에만 의존한다 |
| **결론의 닻 내림.** 한 검토자의 판단이 다른 검토자를 끌고 간다 | 비평가는 다른 비평가의 `challenge`·`verdict`를 보지 못한다. 헌터는 `verdict`를 아예 보지 못한다 |
| **중복 조사** | `claim`과 `dead_end` |
| **변조** | 글의 `id`는 내용의 해시다. 수정된 글은 `sync`에서 걸러져 `board.rejected.jsonl`로 간다 |
| **비밀 유출** | 자격 증명, 환경 변수 값, 대상 밖 경로는 올리지 않는다(브리프 규칙). 도구가 강제하지는 못한다 |

마지막 줄은 도구가 아니라 규칙에만 기대는 부분이다. 그래서 보드는 실행 디렉터리(리포 밖)에 두고, 리포에는 조정자가 검토한 `sync` 결과만 커밋한다.

## 3. 체인 계획

`chains.py`는 capability 뷰를 받아 체인 **가설**을 만든다.

```bash
python3 security/redteam/chains.py plan --capabilities security/redteam/registry/capabilities.json --out security/redteam/registry/chain-candidates.json
```

- 각 노드는 필요한 능력과 얻는 능력을 `(kind, scope)`로 적는다. `kind`는 ZeroMDASH의 통제 어휘 20개 중 하나다.
- 체인은 노드의 순서열이다. 모든 필요 능력이 공격자의 진입 능력이나 앞 노드가 얻은 능력으로 채워지고, 마지막 노드에 직접 영향이 있어야 한다.
- 매칭은 `(kind, scope)` 완전 일치만 한다. `custom`은 자동으로 이어 붙이지 않는다.
- 탐색은 유계다(길이 4, 능력당 후속 4, 빔 64, 후보 200). **결과는 전수가 아니고**, 잘린 수가 출력에 남는다.
- 구성 요소 중 하나라도 확인되지 않았으면 `blocked_on_unconfirmed_components`다. 전부 확인됐을 때만 `ready_for_chain_review`가 된다.

현재 산출: 가설 21개, 전부 `blocked`. run-1 후보가 모두 미검증이기 때문이다. 눈에 띄는 것:

| 진입 위치 | 체인 가설 | 닫히면 |
|---|---|---|
| 인접 네트워크 클라이언트 | 전 인터페이스 바인드 → `/plot_file/` 또는 `db_path` | 운영자 파일 읽기 |
| 운영자 브라우저의 임의 사이트 | CORS `*` → `db_path` | 다른 실행의 DB 읽기 |
| 결과 디렉터리를 건넨 사람 | 뷰어 DOM XSS → `/plot_file/` | **보는 사람** 머신의 파일 읽기 |
| 체크포인트를 건넨 사람 | 시각화 `innerHTML` → manual 답변 엔드포인트 | 운영자 계정으로 코드 실행 (manual 모드일 때) |
| 다른 로컬 사용자 | vLLM 포트 선점 → 마커 위조 | 다른 사람 실행의 점수 조작 |

**이 표는 가설이다.** capability 뷰는 조정자가 후보 설명을 읽고 손으로 붙인 것이고, "A가 주는 능력이 정말 B가 요구하는 그 능력인가"(같은 객체, 같은 주체, 같은 출처)는 체인 조사에서 간선마다 확인해야 한다.

## 4. 팀과 라운드

### 4.1 팀 규모는 코드베이스가 정한다

팀 크기는 고정값이 아니다. `teamplan.py`가 작업 단위를 세고 거기서 인원을 계산한다. 기본 하한은 **라운드당 30명**이다.

```bash
python3 security/redteam/teamplan.py plan --target . --out security/redteam/plans/round-1.json
```

| 작업 단위 | 어디서 오나 | 우선순위 |
|---|---|---|
| seam | 레지스트리의 seam마다 하나 | 가장 높음 |
| lead | 보드에 올라왔는데 주인이 없는 `lead` | 가장 높음 |
| deferred | 이전 실행이 조사하지 않았다고 남긴 커버리지 유닛 | 높음 |
| shard | 범위 내 소스를 무게 상한으로 자른 조각. 무게 = 줄 수 + `risk_weight` × 위험 sink 패턴 적중 수 | 위험 밀도 순 |

```
헌터        = 이번 라운드에 유지한 작업 단위 수 (+ 2차 의견)
비평가      = ceil(헌터 / critic_ratio)          기본 3명당 1명
체인 조사자 = min(체인 가설 묶음 수, chain_top_k)   기본 최대 8
팀          = 헌터 + 비평가 + 체인 조사자
```

- **코드가 크면 늘어난다.** 조각 수는 줄 수에 비례한다. 위험한 sink가 몰린 파일은 무게가 커져 더 잘게 쪼개지므로, 위험한 곳에 헌터가 더 붙는다. 무게 상한보다 큰 파일(예: 18,000줄짜리 `viz_tree.html`)은 줄 범위로 나눈다.
- **하한(`--min-team`, 기본 30)에 못 미치면** 우선순위가 가장 높은 단위부터 독립적인 2차 의견 헌터를 붙여 채운다. 같은 곳을 독립적으로 두 번 보면 한 번에 놓친 것이 나온다. 2차 헌터는 자기 원장을 쓰기 전까지 1차 헌터의 보드 글을 읽지 않는다.
- **상한(`--max-team`, 기본 120)을 넘으면** 우선순위가 가장 낮은 조각부터 보류하고 계획에 목록으로 남긴다. 조용히 버리지 않는다. seam·lead·deferred는 마지막까지 남는다.
- **`--max-concurrency`(기본 30)** 는 한 번에 띄우는 수다. 라운드는 사냥 → 비평 → 체인 순서의 단계로 나뉘고, 각 단계는 이 크기의 웨이브로 나뉜다.

이 리포(범위 내 329개 파일, 공백 제외 80,021줄, 패턴 적중 1,132곳)에 기본값을 적용한 결과가 `plans/round-1.json`이다.

| 설정 | 작업 단위 | 팀 |
|---|---|---|
| 기본 | seam 11 + deferred 6 + shard 63 | **114** = 헌터 80 + 비평가 27 + 체인 7 |
| `--max-team 40` | 같은 수요에서 조각 56개 보류 | 39 = 헌터 24 + 비평가 8 + 체인 7 |

**비용.** run-1의 헌터 7명은 한 명당 20만~32만 토큰(평균 약 24만 5천)을 썼다. 이 평균으로 어림하면 114명 라운드는 약 2,800만 토큰, 39명 라운드는 약 960만 토큰이다. 실측이 아니라 run-1 평균을 곱한 추정이고, 계획 출력에 같이 찍힌다. 첫 라운드는 `--max-team`으로 상한을 정해 돌리고 결과를 본 뒤 늘리는 편이 낫다.

### 4.2 라운드 사이에 다시 계산한다

```bash
python3 security/redteam/teamplan.py plan --target . --round 2 --board-root <run> --previous security/redteam/plans/round-1.json --out security/redteam/plans/round-2.json
```

- 보드에 올라온 주인 없는 `lead`가 새 작업 단위가 된다. 헌터가 자기 seam 밖에서 본 것이 다음 라운드의 인원으로 바뀐다.
- 이전 라운드에서 결과 파일을 남긴 헌터의 단위는 다시 계획하지 않는다.
- PoC로 구성 요소가 확인되어 `chains.py` 결과가 바뀌면 체인 조사자 수가 따라 바뀐다.
- 대상 코드가 바뀌면 조각 수가 바뀐다.

그래서 라운드마다 팀 크기가 달라진다. 발견이 많은 라운드 뒤에는 늘고, 남은 일이 적으면 하한까지 줄어든다.

### 4.3 30명 이상이 한 보드를 쓸 때

- 배정은 조정자가 계획 파일로 미리 정한다. `claim`은 2차 안전장치일 뿐이다.
- 각 에이전트는 계획의 `subscribe_topics`만 `--topic`으로 읽는다. 80명이 올린 글을 전부 읽지 않는다.
- outbox가 에이전트마다 따로라 동시 쓰기 충돌이 없다.
- 실제로 30명 이상을 한 번에 띄워 본 적은 없다. 보드의 읽기는 모든 outbox를 매번 훑으므로 글이 수천 개가 되면 느려질 수 있다.

### 4.4 작은 팀이 필요할 때

하한은 옵션이다. `--min-team 1 --max-team 8`처럼 주면 작은 팀이 된다.

| 방식 | 에이전트 | 쓰는 때 |
|---|---|---|
| 규모 자동 (기본) | 30명 이상, 코드베이스에 따라 | 전체 범위를 한 라운드에 볼 때 |
| 상한 지정 | `--max-team N` | 비용을 정해 놓고 우선순위 높은 것부터 볼 때 |
| `solo` | 0. 조정자가 모든 역할을 차례로 한다 | 보류 유닛 한두 개, 후속 확인 |

| 역할 | 하는 일 | 보드에 쓰는 것 |
|---|---|---|
| 조정자 | 레지스트리와 원장 관리, seam 배정, `sync`, `chains.py` 실행, 최종 기록 | `directive`, `fact` |
| 헌터 | seam 하나의 가설 원장을 끝까지 | `fact`, `lead`, `primitive`, `dead_end`, `handoff`, `question` |
| 비평가 | 자기가 조사하지 않은 주장을 반박 | `challenge`, `verdict` |
| 체인 조사자 | 체인 가설의 간선을 하나씩 확인 | `chain_candidate`, `fact` |
| PoC 엔지니어 | 승인된 후보의 하네스 작성 | `fact`(증거 경로) |

```
라운드 0  조정자: 레지스트리·보류 유닛·체인 가설에서 seam을 고른다              (에이전트 0)
라운드 1  헌터: seam별 가설 원장. 시작·가설 종료 전·끝에 보드를 읽는다
라운드 2  비평가: primitive와 standalone 주장을 반박. 헌터는 challenge에 최대 2회 답한다
라운드 3  조정자: sync → chains.py → 상위 체인 가설을 체인 조사자에게        (계획은 에이전트 0)
라운드 4  소유자 승인 → PoC 파이프라인 → 증거가 상태를 바꾸면 라운드 3 재실행
```

라운드 4는 기존 승인 게이트(`security/DESIGN.md`)를 그대로 쓴다. PoC가 `reproduced`로 나와 구성 요소가 확인되면 `capabilities.json`의 `status`를 바꾸고 `chains.py`를 다시 돌린다. 그때 `blocked`였던 체인이 `ready_for_chain_review`로 넘어온다.

## 5. 지키는 선

레드팀이라는 이름이 범위를 넓히지 않는다. run-1의 규칙이 그대로다.

- 대상은 이 포크의 소스다. 배포된 서비스, 외부 호스트, 다른 사람의 시스템은 건드리지 않는다.
- 대상 코드 실행은 소유자 승인 후 샌드박스에서만 한다. 더미 데이터만 쓰고, 경계가 넘어갔음을 보이는 최소 관찰에서 멈춘다. 지속성·은닉·영향 확대는 하지 않는다.
- 체인도 같다. 체인 PoC는 간선마다의 관찰을 잇는 것이지 완성된 공격 도구를 만드는 것이 아니다.
- 업스트림 리포와 도구 리포에는 아무것도 보내지 않는다.
- primitive와 체인 가설은 취약점으로 보고하지 않는다.

## 7. 아직 검증되지 않은 것

- **보드와 브리프 v2는 실제 에이전트 실행에 쓰이지 않았다.** 도구 테스트는 통과했지만 에이전트가 규칙대로 쓰는지는 돌려 봐야 안다.
- **capability 뷰는 한 사람의 판단이다.** scope 이름과 "무엇을 얻는가"는 조정자가 붙였다.
- **레지스트리는 `partial`이다.** run-1이 보지 않은 영역은 들어 있지 않다. 인용 위치는 파일 존재와 줄 범위만 기계 검사했다.
- 레지스트리는 ZeroMDASH 스키마의 필수 필드를 갖췄다. 이 환경에 `jsonschema`가 없어 스키마 전체 검증은 하지 못했다.

## 8. ZeroMDASH를 직접 돌리려면

`zeromdash/`에 이 리포용 설정과 사전 공격 표면 문서를 두었다. **실행하지 않았다.** ZeroMDASH는 Claude Code·Codex CLI 같은 코딩 에이전트 런타임과 그 자격 증명이 필요하고, seam마다 조사자·비평가를 띄워 에이전트를 많이 쓴다.

- `zeromdash/agent-config.yaml` — 위협 모델을 `common_focus`로, 팬아웃 상한을 작게 잡았다.
- `zeromdash/preset-attack-surface.md` — run-1의 구조 요약과 seam 목록. `--preset-attack-surface`로 넣는다.
- `zeromdash-repro`는 **쓰지 않는다.** PoC를 만들어 실행하는 도구인데, 이 리포에서 PoC 실행은 승인 게이트를 거쳐야 한다. ZeroMDASH가 낸 발견은 `candidates.json`으로 옮겨 기존 파이프라인에 태운다.

자세한 명령은 `zeromdash/README.md`.
